# Signed action and integrated receipt increment plan

> Design for the next portable-library increment. No action, receipt or full mixed-log replay export exists yet. Review this contract before implementation and keep the app untouched until both public repos are ready and tested.

**Goal:** Make a customer-delegated actor's exact governed intent and deterministic effect attributable, then give the client an integrated receipt that can be checked against a customer-authorized signed history checkpoint. The product continues to enforce its existing operational roles; the library checks portable signed evidence.

## Ground truth

- `src/authority-lifecycle.ts` verifies an independently pinned dual-signed anchor, exact customer-root revisions, active bindings, scopes, class names and a customer-authorized provider key. Its `AuthorityState` is opaque; `authorityStateSnapshot` returns copies. A revision has one canonical history leaf.
- `src/checkpoint.ts` signs a history size/root, authority root, policy epoch, signer and predecessor. Its same-key `verifyCheckpointExtension` does not replay mixed authority/action leaves or handle a root-authorized provider-key rotation.
- `src/history.ts` implements RFC 9162 leaf hashing, inclusion and consistency. An inclusion proof authenticates only an explicitly supplied leaf against an explicitly supplied head; the head still needs independent authority and freshness checks.
- The app's approval route has a current operational authorization check and preallocates a link ID before its transaction; the final timestamp is generated inside the transaction. A governed *effect* can commit to meaningful predeclared IDs/resource/envelope sets while excluding incidental timestamps. Every later product route needs its own effect mapping; this plan does not assert they already have one.
- No action or receipt is currently persisted, issued, replayed or used by the app or observer. A provider-signed historical receipt alone does not establish a globally latest view or reveal an isolated hidden event with no independent retained evidence.

## Journey and states

| Step | Caller | Protocol state before → after | Failure |
|---|---|---|---|
| Prepare | Browser/client | Verified anchor, current binding/revision and retained checkpoint → canonical intent/effect commitments | Untrusted pin, stale binding or non-deterministic effect cannot be called fully preauthorized |
| Sign | Actor's separate P-256 signing key | Exact operation, subject/key/version, scope/class, authority revision, observed checkpoint and previous completed receipt for that key → signed action | Wrong key/purpose, class/scope, stale revision or previous chain rejected |
| Accept | App transaction adapter | Operationally authorized, same verified prior head → one exact completed leaf and governed product effect | Changed retry, duplicate operation, race or failed product mutation rolls back together |
| Integrate | Product history publisher | Committed leaf → provider-signed checkpoint containing it | An unintegrated promise is not a completion receipt |
| Receive | Client | Exact leaf/checkpoint/inclusion evidence → verified integrated receipt and retained next-action chain link | Wrong leaf/index/head, unauthorized provider key or inconsistent prior view rejected |
| Observe | Independent puller | Bounded contiguous leaves and retained pin → replayed action/authority state and reconciled receipts | Missing predecessor, changed leaf or fork becomes a durable finding; no client receipt means isolated suppression can remain invisible |

Release waits for **local committed and integrated evidence only**, never for an independent observer. Strict Enterprise/Government mode adds audit policy/retention/reporting checks, not observer-gated release.

## Wire contract

`SignedAction={statement,signature}` uses an exact, versioned canonical statement with `feedId`, `workspaceId`, `operationId`, `actorSubjectId`, `actorKeyId`, `actorVersion`, `scope`, `actionClass`, `authorityRevision`, `authorityRevisionHash`, `authorityRoot`, `policyEpoch`, `observerPolicyHash`, `intentCommitment`, `effectCommitment`, `observedCheckpointHash`, `previousActionHash:Hash|null`, and `previousReceipt:CompletionReceipt|null`. All opaque IDs/commitments are lowercase 32-byte SHA-256 hex; counters are bounded safe integers; action classes match the authority binding grammar. The scope is exactly the existing `AuthorityScope`. The separate P-256 actor key signs `governance.action` bytes. `actionHash` is a domain-separated hash of the **statement** so a valid ECDSA retry of the same statement retains one operation identity. The app binds its existing operation UUID to `operationId` with a documented domain hash and rejects reuse with changed statement bytes. A caller-supplied hash is never accepted as an opening of the intent or effect: product-specific canonical bodies and actual transaction outcome must match the commitment. Bound canonical receipt, signed action and completed leaf at 8, 16 and 24 KiB respectively, and inclusion paths to the RFC tree height.

The expected authority revision/hash/root/policy must equal the replayed state **at the action leaf position**. A workspace-scoped binding permits a workspace or same-workspace vault action; a vault-scoped binding permits only its exact vault. Subject, actor key ID/version and exact action class must match the active binding. A later revocation does not retroactively erase a previously accepted action, but blocks later actions. The app also checks present operational role/capability and expected transaction head. The actor's observed checkpoint must be independently authenticated by the retained client pin and consistent with the provider's current head; it need not be the immediately preceding physical leaf because unrelated operations may interleave. A stale authority revision cannot be used after a newer authority transition.

For a nonfirst action, the app and client also verify that `previousReceipt.checkpoint` is an authenticated ancestor of **both** the actor's observed checkpoint and the transaction's current head, across the complete signed checkpoint chain. A receipt from a valid but divergent signed branch cannot be accepted merely because its own inclusion proof passes.

The one completed-event leaf is exact canonical `{version:1,kind:'governance.completion',action:SignedAction,effectCommitment}`. Its `effectCommitment` equals the signed expected value. Rejected/canceled/abandoned attempts do not advance the completed stream. Product storage must atomically commit its meaningful governed effect, exact leaf bytes and expected-head transition. Network/email delivery occurs after the transaction; failed delivery does not erase committed evidence. The publisher may return an integrated receipt only after the checkpoint and inclusion path are durable. A later queue wake-up is neither ordering nor independent custody.

A signed receipt proves that the provider logged an actor-signed commitment under a particular head. It does **not** independently prove that the Prisma effect occurred, remains unchanged, or that an encrypted body opens to the committed value. The app's transaction/result-opening checks, real-Postgres crash/race tests and authorized evidence exports must establish those separate facts. The observer labels any effect claim as verified only to the extent it can inspect an authenticated opening; otherwise it reports commitment coverage, not database truth.

`CompletionReceipt` is exact `{version:1,status:'integrated',feedId,operationId,actionHash,effectCommitment,leafIndex,leafHash,checkpoint:SignedCheckpoint,inclusionProof:Hash[]}`. It has no pending variant, previous receipt, action or leaf bytes. It is signed indirectly by the provider checkpoint. A domain-separated `completionReceiptHash` identifies **these exact bytes**, but is not the stream predecessor: two valid signed heads or inclusion proofs can yield different receipts for the same completed leaf. The product persists and returns one immutable canonical receipt byte-for-byte on retries. The verifier compares `leafHash` with `hashLeaf` of the **fetched canonical leaf bytes**, checks action/effect/operation identity, inclusion, authorized checkpoint signer at that historical head, reconstructed history size/root and authority root/policy, and the actor's binding at the action position. The verifier starts from an independently pinned, signed size-zero genesis checkpoint and obtains **every intermediate signed checkpoint statement** through the receipt head (or from the client's retained head forward). It verifies each exact `previous` hash, historical customer-authorized provider signer, replayed authority state and RFC consistency. A single direct consistency proof from an arbitrary old head cannot replace the immediate-predecessor chain, especially across key rotation. A raw `verifyCheckpoint` call or a hash-only receipt is not full semantic completion verification. To avoid a leaf↔receipt cycle, the receipt is off-leaf and carries no previous leaf or receipt.

The one completed-operation stream is derived from the **customer-bound actor signing key ID**; the actor cannot supply an arbitrary fresh stream identifier. A new device obtains a distinct customer-root-signed subject/key binding, with an explicit first-operation null predecessor. A root-authorized regrant uses a fresh key and starts a new stream; the authority revision records that transition. The next action under the same key embeds its previous **bounded integrated receipt** and its stable `previousActionHash`, which must equal that receipt's `actionHash`. The observer fetches that prior leaf by index from contiguous source history or an independent archive, matches its RFC leaf hash, operation/action/effect identities and actor key, and validates the prior receipt's checkpoint/inclusion and consistency toward the current head. Missing prior bytes remain an unresolved gap; a later published continuation reveals the missing predecessor's signed head even when the source withholds the earlier receipt. The first completed action under a key has both predecessor fields `null`; replay allows this only once per key. The app enforces one key head with an expected-`actionHash` compare-and-swap and idempotent retries. Different valid receipts for one prior leaf do not create distinct stream heads; the previous action hash is the chain identity. Embedding the receipt exposes the previous opaque operation ID, effect commitment, index and checkpoint timing/size, but never its private evidence opening. Commitments to guessable values require audience-specific salt. A customer-controlled, asynchronous receipt archive can reveal a suppressed event even without a later action; source-only polling cannot guarantee that.

## Changes and proposed names

| Path/name | One responsibility | Name decision |
|---|---|---|
| `src/action.ts` `signGovernanceAction` | Sign one exact action statement | Keep; separate from acceptance |
| `verifyGovernanceAction` | Check actor signature/binding against a supplied historical `AuthorityState` | Keep; does not claim app-role or latest-view verification |
| `governanceActionHash` | Stable statement identity across ECDSA retries | Keep |
| `governanceCompletionLeaf` | Canonical completed-event leaf bytes | Keep |
| `src/completion-receipt.ts` `verifyReceiptInclusion` | Check exact leaf, receipt fields and RFC inclusion under a supplied signed head | Keep name scoped: caller must separately authenticate head/replay |
| `completionReceiptHash` | Identify one exact integrated receipt artifact | Keep; do not use as stream head |
| `src/replay.ts` (later increment) | Replay mixed contiguous leaves and authenticate checkpoint against pinned authority state | Required before observer/app readiness; design API after action/receipt implementation |
| `test/action.test.ts`, `test/completion-receipt.test.ts` | Pure positive, negative and mutation fixtures | Lowest layer |

Avoid a generic policy engine, server-only Node import in the browser root, extra crypto package, or a separate app permission system. If verifier names need `And...` to be truthful, split signature/authority, inclusion/head and full replay claims into separate functions.

## Test-first plan

1. Write missing-export tests for canonical action statement, purpose-bound signature and binding/scope/class checks; observe red. Implement minimum action module. Break key/version/class/scope/authority-revision checks individually and confirm targeted failures, then restore.
2. Test signed statement/effect versus completed leaf: exact operation, effect, version, extra/accessor fields, malformed hashes, changed payload, duplicate operation ID at a product-adapter fixture. Confirm byte-identical canonical round trip; distinguish meaningful governed effect from incidental database timestamps.
3. Write receipt inclusion tests before implementation. Use independently constructed RFC history roots with interleaved authority and completion leaves, check exact leaf index/hash, size/root, swapped receipt/leaf and tampered proof. Construct two valid receipts for the same leaf under different valid heads/proofs: their artifact hashes may differ, but both name the same predecessor `actionHash`. A helper that checks only inclusion must be named/documented as such; do not label it fully witnessed.
4. Add a mixed-history replay fixture that folds the pinned anchor, authority revisions, action, completion leaf and checkpoint, including provider-key rotation and two actor keys. Reject stale authority, revoked/reset actor, validly signed wrong authority root/policy, **wrong checkpoint signer**, skipped/reordered leaves, bad predecessor/consistency, a prior receipt from a divergent signed branch, and missing receipt-chain link. This fixture becomes the contract for the later `replayGovernanceBatch` implementation.
5. Run `pnpm test`, `pnpm typecheck`, `pnpm build`, browser root import, Node `./server` import, `git diff --check`, independent spec and quality review. Storage concurrency, crash and mail ordering require product/observer integration tests later; pure tests do not establish them.

## Principles, smells and verification

SRP: library verifies portable action/receipt facts, product maps business effects and enforces its existing role checks, observer independently replays/pins. DRY: one canonical signature and history implementation. YAGNI/KISS: one integrated receipt status and one action grammar, no pending receipt or second authorization engine. Boy Scout cleanup stays within touched files and separate from behavior changes. No app source changes occur in this increment; app gates apply after integration.
