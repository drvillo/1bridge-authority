# Recipient-key commitment in authority bindings

Status: pure-library correction implemented and independently reviewed before D1 integration. `ActiveBinding` now authenticates a P-256 action key and commits to an exact 1Bridge X25519 recipient-key claim. The app has not yet opened that claim against an actual row; no app key or grant was changed by this library increment.

## Ground truth

- At the time of initial planning, `src/authority-lifecycle.ts` defined active actor bindings with subject, P-256 SPKI/key ID, version, scope and action classes but no recipient-key field. The accepted increment added mandatory `recipientKeyCommitment:Hash|null` and root-signed update semantics; this historical gap is now closed in the library only.
- The app's `WorkspaceMembershipKey` has workspace/membership IDs, row ID, version, `keyId`, `keySuite`, `publicKey`, state and wrapped private key (`ubo-guard/webapp/prisma/schema.prisma:1080-1102`). Its key ID is canonical base64url SHA-256 of the raw X25519 public key, checked by `@drvillo/webcrypto-seal` (`ubo-guard/webapp/src/lib/workspaces/operator-provisioning.ts:108-113,1655-1675`); it is **not** the library's lowercase-hex `Hash` type.
- Existing X25519 possession challenges, wrapping and grants remain operational. D1 needs a customer-root-signed link from actor/device authority to the exact recipient-key version for protected recipient selection; a server-supplied P-256 signing key alone cannot prevent X25519 substitution.

## Contract

Add a mandatory `recipientKeyCommitment:Hash|null` to every active `AuthorityBinding`. `null` means this binding does not authenticate a recipient/decrypt key (for example an admin-only actor); it must not be interpreted as permission to use any key. A non-null value commits the app's exact canonical `RecipientKeyClaim`:

```text
{version:1,workspaceId:<authority 64-hex>,membershipId:<domain-mapped 64-hex>,membershipKeyRowId:<domain-mapped 64-hex>,membershipKeyVersion:<positive safe integer>,keySuite:'x25519',keyId:<canonical existing base64url fingerprint>,publicKey:<canonical existing X25519 public-key envelope>}
```

The commitment is `SHA-256(UTF8('1bridge.authority/v1/recipient-key\n') || canonicalBytes(claim))`, lowercase 64-hex. The pure library exports `recipientKeyClaimHash` for this exact fixed profile, not a generic arbitrary-object hash. `publicKey` starts with literal `v3.x25519.` followed by canonical unpadded base64url of exactly 32 nonzero raw bytes. `keyId` is canonical unpadded base64url of SHA-256 of those raw bytes (43 characters); `keySuite` is exactly `x25519`. The helper verifies these relations with native WebCrypto and rejects malformed/extra fields before hashing, with no runtime crypto dependency. The app also validates `publicKey`/`keyId` through its existing `@drvillo/webcrypto-seal` helper, opens the claim from the actual active `WorkspaceMembershipKey` row, compares every field and commitment to the current customer-root-signed active binding, then selects that exact public key for packaging. A client independently repeats the same comparison before encryption/import. A server-supplied different key, version, membership or row fails even if it has a valid X25519 fingerprint of its own. An observer with the authorized opening can recompute the commitment; without the opening it reports commitment coverage only. Public actor bindings may disclose the hash, not the recipient tuple itself.

The authority library's planned `authorityId` helper, specified in `docs/authority-id-plan.md`, maps app UUIDs; the app adapter supplies actual model IDs. For each app UUID, accept canonical hyphen positions and hexadecimal digits, fold A–F to lowercase, and hash `UTF8('1bridge.authority/v1/id/' + kind + '\n' + lowercaseUuid)` with SHA-256. The fixed `kind` list is `workspace`, `vault`, `membership`, `membership-key-row`, `operation`; reject braces, missing hyphens and non-UUID strings. `RecipientKeyClaim.workspaceId`, `membershipId` and `membershipKeyRowId` are these mapped 64-hex values. The app and independently run observer use the one exported helper and published fixed vectors for this byte contract, not duplicate undocumented mappings. This mapping is pseudonymous only: an observer that knows a UUID can derive its ID.

The pure library validates the `Hash|null` field, includes it in exact signed binding bytes and ordered-map value hash, and hashes a strict public-key claim; it does not import the app's X25519 package or assert private-key possession. A root-signed authority `update` can change the commitment in protocol terms while preserving the P-256 actor key and increasing **binding version**, but the current app has no general membership-recipient-key replacement flow; D1 binds current rows and leaves replacement for a separately specified migration. `membershipKeyVersion` is the row's own counter and must match `WorkspaceMembershipKey.version`, independently of authority-binding version. A workspace-scoped X25519 key may appear under a vault-scoped actor binding, but the actor may use it only for that binding's vault/action classes. Every recipient-selection/wrapping path compares the selected latest active row with the current trusted binding and opens this exact claim; a database row chosen solely by recency is not authenticated authority. A revocation retains the signing-key/version tombstone and no active recipient claim. An authority reset clears active claims. Existing authority fixtures must update their exact active binding shape; no old V1 deployed binding exists because the package is experimental and the app has not integrated it. Freeze this wire format before a product release.

For a protected new-key activation, the browser preallocates the membership-key row UUID before it signs the claim, including in onboarding, invite and existing-member paths that currently let Prisma generate it. The app's existing key-possession challenge remains mandatory. One short guarded transaction checks the exact signed revision/expected head and row tuple, consumes the challenge, inserts the row with that preallocated ID, appends the authority revision/leaf and marks protected status; failure rolls all of them back. A signed proposal that was never accepted is not an on-log binding; retry with the same operation ID and exact bytes returns the same result, while changed bytes or a stale head reject and require a newly signed proposal. For an already active legacy row, the customer signs the current exact row claim and one guarded upgrade transaction appends the binding without re-creating the key. No pending/orphan row is exposed as protected. An operational revocation that cannot obtain a customer-root signature must remove the protected-current claim and report a pending authority update rather than pretend the public map is already revoked.

## Test-first and verification

Write a failing lifecycle test for a binding carrying a recipient commitment, then implement the exact field. Reject missing/invalid/extra field; verify null cannot be mistaken for a non-null key, changed commitment alters map root and invalidates a signed revision. Add fixed X25519 raw-key/envelope/fingerprint/claim/hash vectors computed independently with the app's existing wire helper; reject changed row/version/workspace, malformed envelope, wrong key ID, zero public key and other suites. Break field inclusion in `authorityBindingHash` deliberately and watch a fixed commitment/map test fail. Run full package tests/typecheck/build and browser anchor/replay smoke; obtain separate spec and quality review. The app later adds cross-repo claim vectors and real-DB atomic activation tests for **all** active-key writers and recipient selection before making a protected claim.
