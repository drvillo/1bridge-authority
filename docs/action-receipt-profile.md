# Signed action and integrated receipt profile

This increment defines portable evidence for a completed governed operation. It does not publish a history, authenticate a supplied checkpoint, inspect application database effects, or replay an entire authority/action feed. Those responsibilities belong to the product adapter and later mixed-log replay.

## Action

`SignedAction` is `{statement,signature}`. The version-1 statement is an exact canonical JSON record with `feedId`, `workspaceId`, `operationId`, `actorSubjectId`, `actorKeyId`, `actorVersion`, `scope`, `actionClass`, `authorityRevision`, `authorityRevisionHash`, `authorityRoot`, `policyEpoch`, `observerPolicyHash`, `intentCommitment`, `effectCommitment`, `observedCheckpointHash`, `previousActionHash`, and `previousReceipt`. IDs and commitments are lowercase 32-byte SHA-256 hexadecimal strings. The observer-policy commitment is nullable. Counters are nonnegative safe integers, except the actor key version, which starts at one. An action class follows the authority binding grammar. The signed action is at most 16 KiB.

`signGovernanceAction` signs the exact statement with the separate actor P-256 key using the `governance.action` purpose. It checks that the signing key ID agrees with the declared actor key, but does not claim that the signer is currently authorized. `verifyGovernanceAction` verifies the signature, exact active customer-root binding, key/version, action class and permitted scope against an explicitly supplied historical `AuthorityState`. The supplied state must already have been obtained by pin-first anchor verification and ordered revision replay at the action's position. A workspace binding permits workspace and same-workspace vault actions. A vault binding permits only its named vault. Later revocation does not invalidate an earlier action when it is checked against its earlier state.

`governanceActionHash` is SHA-256 of `1bridge.authority/v1/action-id\n` followed by the canonical **statement** bytes. Re-signing the same statement gives the same stream identity even if ECDSA signature bytes differ. The product must bind its existing operation UUID to the 32-byte operation ID by a documented domain hash and reject changed retries for that operation. The library does not accept an opaque commitment as proof of what the intent or effect body contained. A product-specific canonical opening and actual committed result must be compared separately.

The actor stream is determined by the customer-bound signing key ID. A first action has both predecessor fields `null`. For a continuation, `previousActionHash` must equal the embedded integrated `previousReceipt.actionHash`, and the receipt must name the same feed. This is only a local structural link. Full replay must fetch and validate the previous completed leaf, authenticate the prior checkpoint against the customer's pinned authority, prove its inclusion and ancestor relation toward the current head, and enforce the first-action/one-head rule for each key. The product transaction must compare-and-swap the key's last completed action hash; the library alone does not serialize writers.

## Completion leaf and receipt

`governanceCompletionLeaf` produces exact canonical bytes for `{version:1,kind:'governance.completion',action:SignedAction,effectCommitment}`. The duplicated effect commitment must equal the actor-signed value. The leaf is at most 24 KiB. Its construction validates syntax and size; it does not verify the actor signature or the database effect. An application must commit its meaningful governed effect, exact leaf bytes and expected history-head transition atomically before returning a completion receipt. Incidental timestamps can be excluded only when a documented effect schema says so.

`CompletionReceipt` is an exact, at-most-8-KiB canonical artifact with `{version:1,status:'integrated',feedId,operationId,actionHash,effectCommitment,leafIndex,leafHash,checkpoint,inclusionProof}`. There is no pending receipt. The receipt carries no completed leaf bytes and no previous receipt. It is identified by SHA-256 of `1bridge.authority/v1/completion-receipt-id\n` and its exact canonical bytes. This artifact hash is not the actor stream predecessor: two valid signed heads or proofs can yield different receipts for one leaf; both contain the same `actionHash`.

`verifyReceiptInclusion(receipt, fetchedCanonicalLeaf, suppliedSignedHead)` checks exact receipt/head equality, exact canonical completion-leaf shape, matching operation/action/effect identities, RFC 9162 leaf hash and inclusion path under the supplied head. **It does not authenticate the head or verify the action signature.** Full semantic verification requires an independently pinned, dual-signed anchor, every intermediate signed checkpoint and authority revision through the receipt head, historical provider-key authorization, reconstructed history roots, predecessor links and consistency. A checkpoint signed by an unauthorized key can still pass this inclusion-only helper. A provider-signed receipt proves that the provider logged a signed commitment under a particular head; it does not prove that the corresponding database effect occurred or that a private body opens to the commitment.

An independent observer or customer-retained receipt can later compare competing signed heads and reveal a fork or a source-suppressed event. A source-only observer cannot detect an isolated event that the source never exposes and for which no independently retained evidence exists. Neither this library increment nor OpenTimestamps makes that stronger claim.
