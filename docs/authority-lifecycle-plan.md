# Customer authority lifecycle increment plan

> Implementation record for the portable authority lifecycle. Independent specification and quality review and the package test/typecheck/build gates passed on 2026-10-14. The later recipient-key binding increment in `docs/recipient-binding-plan.md` extends the active binding wire shape described below. The library verifies a supplied, independently authenticated pin; it does not authenticate a customer's real-world identity or enroll anyone in the app.

**Goal:** Define a deterministic, portable customer-held authority anchor and signed binding/revocation/reset transitions whose resulting ordered-map roots can be replayed by a client or independent observer. This supplies D1's authority core and the D4 recovery interface without changing existing app roles or encryption keys.

## Ground truth

- `src/signatures.ts` provides purpose-separated native ECDSA P-256 signatures and key fingerprints. `src/ordered-map.ts` computes a deterministic ordered map root with presence/absence proofs. `src/checkpoint.ts` signs provider history/authority roots. These modules do not yet state who may change a customer's authority map.
- `docs/protocol-design.md` defines separate customer root and recovery authority, historical replay, and exact map/history binding as a design contract, not implemented behavior.
- The application still enforces operational roles from workspace/vault memberships; the portable authority is an additive evidentiary control. Exact app authorization mapping must be checked against current route/lib/Prisma behavior before app edits.
- A root obtained only from the provider is not independently trusted. This library can verify a supplied pin; customer enrollment and pin distribution require a separate app plan and client trust profile.

## Journey and states

| Step | Caller | State before → after | Failure |
|---|---|---|---|
| Establish anchor | Independently trusted customer ceremony | Customer root and distinct recovery public keys, feed/workspace identity, initial empty map → independently delivered pin and epoch 0 | Missing root/recovery possession proof, same key in two roles, malformed key, wrong feed or pin rejected |
| Bind actor | Customer-root signer | Prior map/revision → exact subject/key/version/capability binding and next map root | Stale predecessor, duplicate live key/version, wrong root signature or root mismatch rejected |
| Revoke actor | Customer-root signer | Live binding → retained revoked tombstone and next map root | Unknown/stale binding, wrong signer or root mismatch rejected |
| Change audit policy | Customer-root signer | Signed observer-policy commitment → next policy epoch, same authority map | Missing policy body, stale epoch, wrong signer or mismatched commitment rejected |
| Rotate publisher key | Customer-root signer | Current checkpoint signer → customer-authorized new signer bound to same feed | Missing rotation leaf, wrong customer signature or unverified new checkpoint rejects |
| Reset after root compromise | Independently held recovery signer | Old root/epoch → new root and strictly higher epoch, old actor bindings invalidated | Old online root alone, unchanged root, stale epoch or predecessor rejected |
| Verify history | Offline client/observer | Independently pinned anchor plus ordered mixed-event history → reconstructed authority root and epoch match signed checkpoint | Missing, duplicate, mutated, reordered or checkpoint-mismatched revision stops replay |

These states are portable protocol states, not claims about existing Prisma enums. Recovery of decryption secrets is outside this increment; reset authorizes a new identity/control path only. Existing ciphertext remains subject to existing keys/backups/surviving decryptors.

## Wire and state contract

One `AuthorityAnchor` v1 binds `feedId`, `workspaceId` (opaque 32-byte hash), customer root signing SPKI and fingerprint, distinct recovery SPKI and fingerprint, the initial provider checkpoint-signing SPKI and fingerprint, `policyEpoch:0`, initial `observerPolicyHash:null`, and the protocol's empty ordered-map root. All three keys are distinct. The empty initial map is deliberate: every actor starts with a separately signed revision. `SignedAuthorityAnchor` contains purpose-separated root **and recovery** possession signatures over the exact anchor. The pin is a domain-separated hash of exact canonical anchor *statement* bytes, obtained independently. Verification requires this expected pin as a mandatory argument and checks both possession signatures before returning an opaque verified replay state. A root signature proves possession, but does **not** independently authenticate the organization's real-world identity. The provider checkpoint key is authenticated by its presence in the independently pinned, customer-signed anchor; that provider key does not sign authority enrollment. A freshly installed device must import an independently authenticated pin; accepting a replacement anchor or checkpoint key from the provider alone is an error.

One `AuthorityRevision` v1 binds feed/workspace, a revision number that is **exactly the prior number plus one** (the first revision after the anchor is 1), expected prior revision hash and map root, expected policy epoch, operation, exact resulting map root and policy epoch, signer key ID and purpose-separated signature. Binding operations use one exact canonical discriminated `AuthorityBinding`: active is `{subjectId,keySpki,keyId,version,scope,actionClasses,recipientKeyCommitment,status:'active'}`; revoked is `{subjectId,keyId,version,status:'revoked'}`. The mandatory `recipientKeyCommitment` is a lowercase 64-character hash or `null` for an administrator-only actor; its exact opening is specified in `docs/recipient-binding-plan.md`. `subjectId`, `workspaceId`, `vaultId` and `keyId` are lowercase 64-character SHA-256 hex. Scope is exactly `{kind:'workspace',workspaceId}` or `{kind:'vault',workspaceId,vaultId}` and `workspaceId` must equal the anchor's. Action classes are 1–32 sorted unique ASCII strings, each at most 64 bytes and matching `^[a-z][a-z0-9]*(?:\.[a-z][a-z0-9]*){1,3}$`. They are opaque exact-match identifiers until the app's separately reviewed D1 route/action mapping is defined; the library authorizes a signed action only when class and resource scope match a live binding at its referenced authority revision. Workspace scope covers resources within that same workspace; vault scope covers only the named vault. V1 has no wall-clock expiry: the binding is valid from its accepted revision until a later revocation/reset. A binding update/revocation requires the **current customer root** signature. No actor's ordinary action key may amend its own authority entry.

The binding transitions are exact: `bind` requires current absence and creates active version `highWater+1` (initially 1) with a never-used actor key; `update` requires current active and creates active version `old+1` with the **same** key ID/SPKI but may change scope/actions; `revoke` requires current active and creates the revoked tombstone version `old+1` with the old key ID; `regrant` requires current revoked and creates active version `old+1` with a fresh never-used key. A reset clears the current map, retires all current actor keys, retains per-subject high-water versions and prior key IDs, and preserves the current `observerPolicyHash` while advancing the policy epoch. A later root-signed policy revision can change that hash. An absence proof means that subject has never been bound in the current epoch; it never means a previously bound actor was silently deleted. The replay state retains high-water subject versions and every retired actor/privileged key ID across recovery resets; no old exposed key can be silently reused in a new epoch or another role. Root, recovery, checkpoint and actor key IDs must be pairwise distinct, including across prior roles. The state snapshots returned to callers are copies; mutation cannot change verification state.

An independent recovery reset is a revision signed by the **current recovery key**, names fresh distinct customer-root and recovery keys, includes new-key possession signatures, increments the policy epoch exactly by one, preserves `observerPolicyHash` and produces the empty map root. This deliberately invalidates old actor bindings until regranted and retains all historical subject-version/key-use evidence. A previous recovery key cannot sign later epochs. Recovery credentials are prepared and held independently before an incident. If both root and recovery authority are lost, the library reports irrecoverability rather than admitting a provider reset.

A root-signed audit-policy revision carries an exact canonical JSON observer-policy body of at most 8 KiB and commits its domain-separated hash (or uses `null` body/hash to disable), increments the policy epoch exactly by one, and leaves the map root unchanged. The body defines observer identity/pin, reporting/retention and strict-audit terms in the later D3 policy profile; this increment verifies the hash/transition but does not interpret those terms. An observer must obtain and interpret the body to claim policy compliance. The initial `null` means no configured observer. Neither this policy nor its epoch gates a release. A distinct root-signed checkpoint-key rotation revision binds a fresh provider P-256 key ID/SPKI to the same feed, leaving map root and policy epoch unchanged; historic and current key IDs remain in replay state so they cannot be silently reused.

Use existing `orderedMapRoot` and canonical `sha256` commitments. Choose and document a single domain-separated map key derivation from opaque subject ID and one exact value hash of `AuthorityBinding`. Keep complete canonical binding records and retired-key/version ledger for replay; the map root alone does not disclose the current record. Cap one serialized revision at 16 KiB, one batch at 1,024 revisions, current subjects at 10,000, and all counters at nonnegative safe integers; overflow rejects. Reject getters, mutated objects, duplicate fields/subjects, noncanonical serialized forms, unknown operations and wrong-purpose signatures.

Each accepted revision is represented by exactly one canonical history leaf `{version:1,kind:'authority.revision',revision:<signed revision>}`. A provider log may interleave action, receipt and policy leaves, but a verifier processes leaves in exact index order. It parses canonical bytes, applies each authority revision before any later action that cites it, and reconstructs the RFC 9162 history root/size and final authority map root/policy epoch at each checkpoint. A checkpoint is accepted only if its provider signature is made by the **currently customer-authorized checkpoint key**, its append-only extension validates, and its size/historyRoot/authorityRoot/policyEpoch equal these reconstructed values. `verifyCheckpointExtension` alone is insufficient. The first checkpoint uses the checkpoint key from the independently pinned anchor and empty history/map. A key-rotation leaf is verified under the customer root before the new key can sign the next checkpoint; a cross-key extension uses the old/new verified signatures, exact predecessor hash and RFC consistency proof, rather than the current same-signer-only `verifyCheckpointExtension`. This increment includes a cross-module fixture test with mixed no-op/action leaves and wrong signed authorityRoot/epoch and unauthorized new signer; the future action/receipt increment will own a complete `replayGovernanceBatch` API.

**Critical freshness limit:** a valid historical root establishes past authority at that revision. Neither it nor an isolated inclusion proof proves it is globally latest. A client needs its retained pin/checkpoint and an acceptable freshness policy; the observer verifies contiguous published history against its own pin. The product must not upgrade legacy membership to authenticated customer authority without the customer's anchor ceremony.

## Changes and proposed names

| Path/name | Responsibility | Name decision |
|---|---|---|
| `src/authority-lifecycle.ts` `createAuthorityAnchor` | Validate an independently supplied root/recovery pair and create one anchor statement | Keep: single record creation |
| `signAuthorityAnchor` | Add both customer-key possession signatures | Keep: one anchor certification step |
| `anchorHash` | Compute the exact customer pin from an anchor | Keep: one hash |
| `verifyAuthorityAnchor` | Require expected independent pin and both key proofs; return an opaque state | Keep: only trusted replay entry point |
| `signAuthorityRevision` | Sign one prepared transition with a customer-controlled key | Keep: signer authorization remains replay-checked |
| `applyAuthorityRevision` | Verify and apply one transition to an opaque verified replay state | Keep: one state transition |
| `replayAuthorityRevisions` | Verify pin, then fold a contiguous bounded revision list | Keep: expected pin is required, not optional |
| `AuthorityState` | Privately hold epoch, current keys, root, revision hash/index, exact bindings and retired-key ledger | Opaque and immutable to callers |
| `authorityRevisionLeaf` | Produce one canonical RFC-history leaf for an accepted signed revision | Keep: byte contract only, not full history verification |
| `test/authority-lifecycle.test.ts` | Contract, negative and mutation tests | Lowest responsible layer |
| `docs/authority-lifecycle-profile.md` | Wire grammar, custody and limitation statement | Public review contract |

If one module becomes too large or a function name strains to describe authorization **and** map reconstruction, split record validation/hashing from the transition reducer. Do not invent a generic identity framework, new crypto dependency, database schema or app route in this increment.

## Test-first plan

1. Write missing-export anchor tests, observe failure, implement anchor validation/hash, dual possession signatures and mandatory expected-pin verification. Reject provider-substituted anchor, fresh-device provider-only bootstrap, same root/recovery key, wrong curve, alternate encoding, malformed feed and tampering. Mutation of domain tag must fail a fixed expected-hash fixture.
2. Write one valid binding and revocation sequence as the first replay test. Observe red, implement smallest transition reducer. Compare resulting map root to a separately built sorted map oracle; verify presence while active, revoked-tombstone presence afterward, and true absence only for an never-bound subject.
3. Add regrant with fresh key/higher version; negative authorization, predecessor, duplicate, stale version, cross-role/historical key reuse, wrong epoch/feed/workspace, wrong result root, modified/unsorted/duplicate action classes and unknown-operation tests. Add root-authorized publisher-key rotation and reject provider-chosen key replacement. Break one signature-purpose and predecessor invariant deliberately and watch targeted tests fail before restoring.
4. Add recovery reset: only separate recovery key may advance epoch and replace both root/recovery keys with possession proofs, map resets but retired keys/high-water versions persist, old keys cannot act, new root can regrant. Add audit-policy commitment/epoch transition, irrecoverable/no-provider-bypass documentation and wrong-key tests.
5. Add serialized canonical round-trip/adversarial fixtures, caller-output mutation tests, rejection of a sibling revision **relative to a retained head**, and a mixed-history cross-module fixture that rejects a validly signed checkpoint with wrong authorityRoot or policyEpoch. Isolated replay cannot prove another valid sibling branch does not exist. The future action module completes full action verification, but this test proves roots alone are insufficient.
6. Run package tests/typecheck/build, browser root import (no Node-only module leakage), Node server import compatibility and independent spec/quality review. This pure increment has no database transaction claim; later fixture/Postgres tests must establish atomic storage behavior.

## Principles, Boy Scout and verification

SRP: key custody and enrollment ceremony are product/customer concerns; this module verifies portable authority transitions. DRY: existing canonical/signature/map primitives remain the single cryptographic implementations. KISS: root-signed changes and one recovery reset rule, without recursive delegation or threshold custody. YAGNI: no provider override or speculative role language. Touched-file cleanup should remain behavior-preserving and separate from behavior changes. Run `pnpm test`, `pnpm typecheck`, `pnpm build`, `git diff --check`, selected browser/Node import checks, and independent review. App gates apply only after app source changes.
