# Blind proof-access profile

This package implements the `RSABSSA-SHA384-PSS-Randomized` profile in [RFC 9474](https://www.rfc-editor.org/rfc/rfc9474.html). It uses a dedicated 4096-bit RSA key with exponent 65537, SHA-384 for PSS and MGF1, a 48-byte PSS salt, and a 32-byte randomized preparation prefix. The browser uses `emBits = modBits - 1`, following [reported erratum 9089](https://errata.rfc-editor.org/eid9089/) and native RSA-PSS verification. The package has no runtime dependencies.

The browser root export provides `importProofAccessPublicKey`, `blindProofAccess`, `finalizeProofAccess`, `verifyProofAccess`, and `proofAccessNullifier`. Importing a public SPKI creates an extractable verify-only RSA-PSS/SHA-384 `CryptoKey` and privately snapshots its modulus and exponent. Later operations accept only that exact returned key. The Node-only `@drvillo/1bridge-authority/server` export provides `signBlindedProofAccess`; it requires a dedicated generic `rsa` private `KeyObject` and checks the raw private operation with its public inverse. Do not use an `rsa-pss` KeyObject or use this private key for any other protocol or encoding profile.

The signed message is exactly ASCII `1bridge.authority/v1/proof-access\n` followed by 32 fresh nonce bytes. RFC preparation prepends a separate 32-byte random value. A token contains only canonical base64url `preparedMessage` and a 512-byte `signature`. Its random nonce, preparation prefix, PSS salt and blind factor come from native randomness. The blind factor is sampled uniformly from `[1,n)` by rejecting out-of-range and noninvertible values. `proofAccessNullifier` is the lowercase SHA-256 hash of ASCII `1bridge.authority/v1/proof-access-nullifier\n` followed by the exact prepared-message bytes. It identifies a one-use token in a later transaction; this library does not record spending.

`blindProofAccess` returns an opaque frozen state handle. The client must keep the handle until `finalizeProofAccess` finishes; an invalid response consumes it and a browser reload loses it. The handle cannot be serialized. The signed message contains no user ID, issuance ID, proof ID, or caller-selected scope.

The application must issue only after an attributable eligibility decision. Separately, an independently trusted customer certificate must bind a **shared cohort key** to one workspace, capability, audience and expiry window. The same key must never be certified for a second scope or renewed for a later window; renewal requires a new key. At redemption, the application must verify the certificate for its **expected** issuer and scope, validate the token with that selected key, then atomically consume its nullifier in the same transaction that grants one proof read. A signature alone conveys no authorization. Product integration needs negative tests for cross-scope use, renewal replay, duplicate certification and concurrent redemption.

Blindness does not hide a user in a one-person cohort or prevent network and timing correlation. Unlinkability requires a cohort of indistinguishable issuances and privacy-preserving redemption behavior. Native private operations need deployment side-channel assessment. The library tests establish functional RFC conformance, not those deployment properties.
